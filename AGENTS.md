# AGENTS.md — wow-hub

Инструкции по этому подпроекту. Читай перед правками.

Общие правила по репаку (бэкапы, запуск, остановка, грабли сборки) — в
`../AGENTS.md`. Здесь — только то, что касается самой панели.

---

## 0. Что это

Панель управления локальным репаком: одно окно вместо трёх консольных, и
главное — **корректная остановка стека в правильном порядке**.

Стек: Go + Wails v3 beta.27 (окно на WebView2), фронтенд — Svelte 5 + Tailwind v4 +
shadcn-svelte, собирается Vite в `frontend/dist`. `wails build` кладёт бинарь
в `wow-hub/build/bin/wow-hub.exe`; в корень репака его нужно скопировать
отдельно (см. раздел 4) — сам он туда не попадает.

Win32 нужен напрямую (консоли дочерних процессов, `GetProcessMemoryInfo`,
владелец порта), и приложение должно быть одним самодостаточным exe без
рантайма — отсюда Wails.

---

## 1. Главный инвариант: порядок остановки

`worldserver` пишет в базу во время выключения. Если MySQL уйдёт первым,
мир останется писать в мёртвое соединение — это и есть путь к потере
несохранённого персонажа. Поэтому:

* **старт**: MySQL → пинг БД → authserver → worldserver;
* **остановка**: worldserver → authserver → MySQL;
* **остановить MySQL, пока работает мир, нельзя.** Проверка —
  `dependentRunning` в `internal/supervisor/stop.go`, в единственной точке,
  через которую проходят все остановки: кнопки в строках, `StopAll` и
  `Restart`. Не переноси её во фронтенд: там она защитит только кнопки.

`StartAll` при провале откатывает **только то, что запустил сам** (adoption
уже работающего MySQL — не повод его гасить). Откат и уборка после
неудачного старта идут через `stopOneUnchecked`: guard там не нужен и вреден,
иначе сломанный MySQL нельзя будет убрать из-за постороннего authserver.

Смена порядка или снятие guard — изменение, которое может стоить
персонажей. Не делай этого без явного запроса.

## 2. Структура

| Пакет | Ответственность |
|---|---|
| `main.go`, `app.go` | сборка зависимостей и Wails-биндинги. Логики нет |
| `internal/repack` | **все** пути, порты и учётные данные репака. Единственный источник правды |
| `internal/osops` | единственная дверь в Windows: `Ops` + фейки |
| `internal/supervisor` | состояние трёх процессов, лестница остановки, старт |
| `internal/health` | шесть проверок для экрана «Проверки» |
| `internal/dbping` | пинг БД |
| `internal/notify` | события в UI (`Sink`); Wails здесь не импортируется |
| `internal/logx` | `logs/wow-hub.log` |
| `internal/backups` | **чтение** папки `backups\`: что там лежит и похоже ли это на копию |
| `internal/realmdb` | **чтение** баз: размеры, счётчики, список персонажей, список аккаунтов. Только `SELECT` |
| `internal/dumps` | **создание** копии: дампы четырёх баз и физический слепок |
| `internal/restore` | **откат** по физическому слепку: остановка стека, страховка, распаковка |
| `internal/prune` | **удаление** точки отката: `RemoveAll` папки, без корзины и без отмены |
| `internal/settings` | `wow-hub.settings.json`: напоминание о копии |
| `frontend/` | Svelte 5 + Vite, встраивается через `go:embed all:frontend/dist`. Оболочка со статусом + три экрана, см. раздел 6 |

Три ступени по «кто что пишет», и они не смешиваются:

1. **Только чтение** — `backups`, `realmdb`. Ни строчки, ни в базу, ни в файлы.
2. **Пишет файлы** — `dumps` (дампы и слепок), `settings` (свой json). В базу не лезет.
3. **Пишет поверх данных** — `restore`. Это единственное место, которое
   заменяет содержимое `mysql\data`, и единственное, где порядок шагов
   нельзя переставлять: стоп → страховка → распаковка. Отдельно от
   «создать» не по эстетике, а потому что откат не повторяем: создание
   можно начать заново, откат — только страховкой.

`prune` стоит между второй и третьей ступеньми: удаление не трогает `mysql\data`
и не требует остановки мира, но это **единственная операция без возврата**.
Корзины нет и не планируется — вопрос, который она решает, снимает окно
подтверждения, где папка названа словами.

Логические дампы откатом из панели **не** восстанавливаются, и это не
недоработка: `restore-all-db.cmd` берёт самую свежую папку с
`acore_world.sql` и молча пропускает базу, файла которой нет. Кнопка
«Восстановить» есть только у строк `Kind === physical`.

Правила, которые уже стоили времени:

* **Пути и порты — только из `repack`.** Абсолютный путь к конфигу
  worldserver не принимает: он хочет `configs/worldserver.conf` относительно
  своего рабочего каталога, поэтому в `Layout` есть `WorldConfRel`/`AuthConfRel`.
* **«MySQL работает» спрашивается у порта, а не у supervisor.** `dumps.checkLogical`
  делает `ops.Listen(repack.MySQLPort)`, и планировщик в `checkSchedule` — тоже.
  Ответ supervisor'а уже: MySQL, запущенный не панелью, он показывает как
  `external`, а дамп с него снимается совершенно нормально. Второй ответ на
  тот же вопрос — это второе, что придётся синхронизировать.
* **Мир переживает закрытие панели, и это стоит целого раздела в
  лестнице остановки.** `worldserver` читает консольные команды из stdin и
  на EOF выключается сам. Панель запускала его с `cmd.StdinPipe()`, и
  писатель трубы жил только в панели — её смерть и была тем EOF. Мир умирал
  через секунды после каждого закрытия панели, без отсчёта, то есть мимо
  цикла сохранения; на одном прогоне умер вообще без игрока-человека.
  Теперь `WinOps.Start` отдаёт ребёнку и писателя тоже
  (`AdditionalInheritedHandles`) — он не используется, просто держит трубу
  открытой, поэтому канал не может дать EOF ни при каком конце панели.
  Крестик, трей и падение панели больше не роняют мир.
* **Но остановить унаследованный мир нечем, и маршрутом это не
  чинится.** Мир, переживший панель, для следующей панели `external`, а
  канал команд у него тот же stdin. Замерено на живом бинарнике: команда,
  напечатанная в его консоль (stdin у него — труба, а не консоль;
  напечатанное лежит в буфере, который никто не читает); `CTRL_C_EVENT` в его
  консоль — **работает не всегда**: один прогон остановил мир, все четыре
  пула закрылись по порядку, следующий не дал ничего за 60 с;
  `CTRL_BREAK_EVENT` — тоже ничего. Два прогона из трёх — это не то, что
  обещать человеку, который сейчас теряет прогресс персонажа, поэтому
  ступенькой эта попытка не стала. Именованная труба вместо stdin тоже не
  годится: она работает, пока клиент подключён, а его отключение даёт
  ребёнку конец потока — та же ловушка под новым именем; второй `CreateFile`
  отвечает `All pipe instances are busy`. Значит унаследованный мир идёт
  сразу к вопросу об убийстве, и **окно подтверждения обязано называть
  цену**: цикл сохранения не выполнится. Старая подсказка «закройте его окно»
  была неверна и для этого случая, и для любого: окно, диалог которого
  открыт, уже исчерпал все штатные пути.
* **Почему MySQL после перезапуска панели останавливается, а мир — нет.**
  Панель гасит MySQL запросом по сети: `mysqladmin shutdown` идёт на порт,
  который слушает сам сервер, и ничего не требует от панели. `worldserver`
  и `authserver` запроса не имеют: их останавливают либо записью в трубу,
  которую держит панель (после её смерти дескриптора нет), либо событием
  консоли (см. выше, работает через раз). Канал, который пережил бы панель,
  у них один и тот же — собственный listening-порт: у мира это **RA**,
  `Ra.Enable = 0` в этом репаке, и он требует учётных данных; у
  `authserver` такого канала нет вовсе. Но это и не страшно: в нём нет
  игровых данных, его убийство ничего не теряет — в отличие от мира.
* **`os.Mkdir`, а не `MkdirAll`** в `dumps.makeLogicalDir`. `Mkdir` падает,
  если имя занято, поэтому папка, полученная оттуда, всегда создана этим
  вызовом. `cleanup` удаляет её целиком — и в существующую папку он попасть
  не должен ни при каких условиях: это была бы чужая копия.
* **Счётчик коллизий идёт ПЕРЕД суффиксом** (`<stamp>_2_current`, не
  `<stamp>_current_2`). `removable` опознаёт папку по суффиксу `_current`;
  имя, которым он не опознаётся, `cleanup` удалить не сможет.
* **`dumps.Physical` слушает отмену.** Архиватор — чистый Go
  (`internal/archive`), внешних процессов нет, и отмена прекращает запись в
  пределах секунды, после чего `cleanup` удаляет недописанную папку. Откат
  (restore) — по-прежнему не отменяем, см. ниже.
* **Память сервиса — это дерево процессов, а не один PID.** `mysqld` на этом
  репаке идёт парой `mysqld.exe`: родитель ~18 МБ, ребёнок (владелец 3306 и
  буферного пула) ~443 МБ. Приложение запускает родителя, поэтому память
  читается через `Ops.TreeMemoryMB` (PID + всё под ним), а для усыновлённого
  сервиса — суммой по найденным PID. Обратно на `MemoryMB(pid)` не откатывай:
  это возвращает строку MySQL с 18 МБ при реальных 461.
* **Память — приватный рабочий набор, а не полный.** Колонка «Память» в
  диспетчере задач показывает `PrivateWorkingSetSize` из
  `PROCESS_MEMORY_COUNTERS_EX2`, и именно с ней человек сверяет таблицу.
  Полный `WorkingSetSize` считает ещё и общие страницы, а у процесса, который
  в основном маппит DLL, разрыв кратный: authserver 4 МБ против 18, `ping`
  1 МБ против 8. Если вернуть полный набор, строка authserver разойдётся с
  диспетчером задач вчетверо, а выглядеть это будет как враньё панели.
  Раскладку структуры держит `TestProcessMemoryCountersEx2Layout`: 96 байт,
  `PrivateWorkingSetSize` по смещению 80. Ошибка в раскладке не падает —
  `GetProcessMemoryInfo` пишет что влезло и возвращает успех, а на экране
  просто неверное число.
* **Байты суммируются, мегабайты округляются один раз.** `MemoryMB` округляет
  до ближайшего мегабайта, но `TreeMemoryMB` складывает байты и округляет
  результат: при округлении каждого процесса по отдельности теряется до
  мегабайта на процесс, а в дереве из двух процессов это и есть вся разница —
  `cmd.exe` с дочерним `ping` может дать в сумме ровно столько же, сколько
  корень один.
* **Флаги запуска mysqld — `mysqlArgs` в `start.go`**, и они должны совпадать
  с `../MySQL.bat`. `mysqld` без аргументов идёт на дефолтах (128M пул, 64M
  пакет, REPEATABLE-READ) и не пишет в лог панели: без `--console` он пишет
  только в `mysql/data/<host>.err`.
* **`wailsSink` — единственный переводчик событий в браузерные.** Supervisor
  не знает про Wails.
* **`Refresh` берёт лок дважды, и между этим есть окно.** Читает `sv.proc`
  под локом, потом СБРАСЫВАЕТ его и собирает наблюдения (`FindByName` →
  `tasklist`, `PortOwner` → `netstat` — сотни миллисекунд), потом берёт лок
  снова и применяет. Старт или остановка, попавшие в это окно, новее
  собранных фактов, поэтому в `service` есть счётчик `rev`: `Refresh`
  запоминает его при чтении и **пропускает наблюдение, если `rev` изменился**.
  Без этого свежий `StateStarting` затирается на `StateExternal`, и только что
  запущенный сервис висит как «запущен извне» до проверки готовности.
  Любой новый код, меняющий статус, обязан инкрементить `rev`
  (`track`, `markRunning`, `markStopping`, `markStopFailed`, `clearLocked`,
  `forget`, ветка выхода процесса).
* **Откат (`internal/restore`) не отменяется, и кнопка «Отменить» на нём
  прячется.** К моменту, когда откат идёт, `mysql\data` уже распаковывается
  поверх — состояние, в котором не работает ни панель, ни человек. Распаковка
  теперь в процессе панели (`internal/archive`), но причина не отменять осталась:
  половина заменённой папки базы хуже отката, доведённого до конца. Страховка
  перед распаковкой (`dumps.Physical`) — единственный путь назад, и он не
  восстанавливает сам себя. Поэтому `CancelBackup` глушит `backupCancel`, если
  `Kind == restore`, а `applyBackupButtons` прячет кнопку, а не просто гасит.

## 3. Wails: правила биндингов

Страница вызывает **`AppService`** (`service.go`), а не `App`. Это единственный
зарегистрированный сервис, и только его экспортированные методы становятся
вызовами из JS; аргументы и результат идут через JSON по `POST /wails/runtime`.

* Ни один метод не принимает `context.Context` — Wails потребует его от
  страницы, и вызов умрёт на `json: cannot unmarshal`.
* Ни один не возвращает канал или функцию — JSON их не умеет.
* Всё, что не должно быть доступно странице, — неэкспортировано
  (`setSupervisor`, `tick`, `askConfirm`).

`TestNoBoundMethodHasAnUnserialisableSignature` в `app_test.go` проверяет это
рефлексией по `AppService`. Не удаляй его и не переводи обратно на `App`:
у `App` больше нет ни одного биндинга, и проверка на нём ничего не охраняет.

Две ловушки v3, обе уже стоили времени:

* **`Events.On` отдаёт объект `WailsEvent`, а не payload.** Восемь подписок в
  `state.svelte.ts` спасены одной обёрткой `EventsOn` в `api.ts`, которая
  снимает `.data`. Кто напишет `Events.On` напрямую — получит объект
  `{name, data, sender}` вместо данных и сломает все восемь сразу.
* **Закрытое окно нельзя воскресить.** `Show()` зовёт `Run()`, а тот выходит
  по непустому `impl`, который закрытие не обнуляет. Возврат — только
  `app.Window.NewWithOptions(...)`; отсюда `newWindow` в `main.go` как
  функция и `sink.setWindow(w)` на каждом новом окне.

`api.ts` разводит типы и функции по разным пространствам имён
(`export type * as main` и `svc.Status`). Метод `BackupStatus()` и тип
`BackupStatus` — одно имя; слей их в один namespace, и TypeScript выберет
один молча, а страница отрендерит пустоту.

## 4. Сборка, тесты, проверка

```bash
cd wow-hub
go vet ./...
go test ./...            # часть тестов поднимает реальные ping.exe / cmd.exe
# после правки AppService — обязательно, и ДО сборки фронтенда:
go run github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-beta.27 \
    generate bindings -ts -d ./frontend/bindings
npm --prefix frontend run build   # dist/, который встраивается в exe
# иконка: appicon.png -> icon.ico -> ресурс в exe. Нужно до go build,
# потому что .syso встраивает линкер, а он читает файлы пакета на старте.
go run github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-beta.27 \
    generate icons --input build/appicon.png
go run github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-beta.27 \
    generate syso -arch amd64 -icon build/windows/icon.ico \
    -manifest build/windows/wails.exe.manifest -info build/windows/info.json \
    -out rsrc_windows_amd64.syso
go build -tags production -trimpath -buildvcs=false \
    -ldflags="-w -s -H windowsgui" -o build/bin/wow-hub.exe .
cp build/bin/wow-hub.exe ../wow-hub.exe   # это и есть запускаемый файл
```

`generate icons` на этом репозитории **заканчивается ошибкой** — она сразу
после `.ico` tries собрать `.icns` и не находит `build\darwin`. Приложение
Windows-only, так что это ожидаемо: `.ico` к этому моменту уже записан.
Ошибку игнорировать можно, `.ico` — нет.

**`-H windowsgui` обязателен.** Без него бинарь линкуется с подсистемой
Console, и при запуске из Проводника рядом с панелью появляется чёрное окно
консоли, которое не закрывается. `wails build` в v2 подставлял этот флаг сам;
с переходом на `go build` он стал нашим, и забыть его — значит показать
пользователю лишнее окно.

Тот же набор флагов стоит в build-файлах самого Wails
(`examples/*/build/windows/Taskfile.yml`), так что он не наша прихоть. Проверять
подсистему, если вдруг снова появится окно:

```bash
powershell -NoProfile -Command "\$b=[IO.File]::ReadAllBytes('wow-hub.exe'); \
  \$pe=[BitConverter]::ToInt32(\$b,0x3C); \
  'Subsystem = ' + [BitConverter]::ToUInt16(\$b,\$pe+0x5C)"   # должно быть 2 (GUI)
```

`-tags production` включает `application_production.go` вместо отладочного, а
`-s -w` убирают символы: бинарь 12 МБ вместо 18.

### Иконка

`build/appicon.png` (1024×1024) — источник, из него `generate icons` делает
`build/windows/icon.ico`. Тёмная плашка и золотая «A» — цвета `--background`
и `--gold` из `app.css`, волосяная рамка — та же, что носит каждая панель.
«A» выбрана потому, что это единственная буква, читаемая в 16 пикселей, а
16 — это трей.

Иконка живёт в трёх местах, и они не дублируют друг друга:

* **в самом exe** — Проводник, панель задач, Alt+Tab. Берётся из
  `rsrc_windows_amd64.syso`, который генерится на каждой сборке и в git не
  лежит. Без шага `generate syso` бинарь собирается, но без иконки.
* **на окне** — из `Options.Icon`, то есть **`.ico`, а не `.png`**. Wails
  отдаёт эти байты в `CreateIconFromResourceEx`, который ждёт данные, читаемые
  как битмап; PNG он принимает как есть, вызов проваливается, и окно молча
  остаётся без иконки. Ошибка там проглатывается, так что «просто не работает»
  и никакого сообщения.
* **в трее** — `tray.SetIcon` с тем же `.ico`, явно, а не подстановкой иконки
  из exe: трей это то, что человек ищет, когда панели на экране нет.

`build/windows/info.json` заполнен значениями, а не шаблонами `{{.Info.*}}`,
как было от v2. Побочно exe получает имя и версию в свойствах файла.

**Проводник после новой сборки показывает старую иконку — это кэш, а не сборка.**
У Explorer база значков `%LOCALAPPDATA%\Microsoft\Windows\Explorer\iconcache_*.db`,
по файлу на масштаб дисплея, и кэширует она **каждый размер отдельно**. Отсюда
странное «уменьшаю ползунок — вижу прежний значок, увеличиваю — вижу новый»:
мелкий размер ещё лежит в кэше, крупный уже перечитан. Через некоторое время
кэш перечитывает файл сам.

Лечится одной командой, без сброса кэша и без закрытия окон Проводника:

```bash
touch wow-hub.exe
```

Сбрасывать весь `iconcache` ради одного значка не надо: это закрывает все
окна Проводника.

`wails build` и `wails.json` больше не участвуют: это формат v2. Вместо них —
`go build` плюс `npm run build`, и порядок именно такой.

`go build` **не** ловит отсутствие `frontend/dist`: `//go:embed all:frontend/dist`
упадёт на этапе линковки, если папки нет. Генерация биндингов нужна **до**
`npm run build`: `api.ts` импортирует сгенерированные модули, и Vite падает на
импорте несуществующего — то есть сборка фронтенда падает целиком, а не в
одном месте. `go build` этого не ловит, потому что `bindings/` для него не
существует.

`frontend/bindings/` в git не лежит (см. `.gitignore`) — она собирается из Go.

`go build` **не** обновляет `wow-hub.exe` в корне репака — только
`build/bin/`. Забыть про `cp` означает оставить пользователю старый бинарь,
и выглядит это как «правки не подействовали». Проверять, что exe свежее
исходников:

```bash
find wow-hub -name '*.go' -newer wow-hub.exe    # вывод должен быть пуст
```

`tools/ui-e2e.mjs` проверяет собранную страницу в Chromium через Playwright.
Он подменяет бэкенд перехватом `POST /wails/runtime`, а не глобальными
объектами: в v3 страница ходит в Go по сети, и заглушка в `window.go`
проверяла бы страницу, которой больше нет. Идентификаторы методов харнесс
читает из `appservice.ts` и `window.js`, поэтому перегенерация биндингов его
не ломает.

Тесты `internal/osops` намеренно запускают настоящие `ping.exe`, `cmd.exe`,
`tasklist`, `netstat` — иначе Win32-обёртки не проверить. Серверы репака они
не трогают.

`internal/supervisor` работает на `osops.FakeOps` и `osops.FakeClock`:
лестница ждёт 30 и 60 секунд, и на реальных часах этот набор тестов никто бы
не запускал. `FakeOps.FindByName` не показывает мёртвые PID — иначе guard
было бы нечем проверить.

`internal/restore` — на настоящем `t.TempDir()`, а не на фейке: весь риск в
нём в разрешении присланного страницей имени в путь, а этот риск живёт в
`os.Stat` и `filepath.Join`, которые фейк не воспроизводит. `Stopper` и
`Snapshoter` в нём — интерфейсы, а не поля на структуре, именно чтобы откат
не научился останавливать мир своим способом и плодить второй формат слепка.

## 5. Про остановку мира и сохранение игроков

Мир останавливается командой `server shutdown 1`, записанной в его stdin.
Это единственный измеренный путь, дающий отсчёт
`Server shutdown in N second(s)` — проход сохранения онлайн-игроков — и
закрытие всех пулов БД. Код выхода при этом `0xc0000374`
(`STATUS_HEAP_CORRUPTION`), и **код выхода не является признаком успеха**.

После остановки мира панель читает `logs/Server_*.log` начиная с позиции,
записанной до остановки, и классифицирует её (`internal/supervisor/worldlog.go`):
`clean` (пулы + отсчёт + Halting) / `partial` (пулы без отсчёта) /
`unknown`. Если не `clean`, пользователю уходит предупреждение событием
`operation`. Не «упрощай» это до «процесс умер = успех».

Разбор сигналов и флагов — `../docs/superpowers/spikes/2026-09-29-ctrl-break.md`.

## 6. Фронтенд: где что живёт

**Статус живёт в оболочке, а не на страницах.** Это главное правило
`frontend/`, и оно появилось не из вкуса. Раньше статус жил внутри страниц, и
каждая страница обзаводилась его копией: две пары кнопок «Запустить всё» /
«Остановить всё», одно и то же состояние, нарисованное в два дерева DOM, и
строка «последнее действие» только на одном экране — том самом, куда писали
глобальные `window.onerror`, из-за чего ошибка интерфейса была не видна со
всех остальных.

Поэтому в оболочке осталось только то, у чего нет другого дома: нижняя полоса —
строка последнего действия и кнопка обновления. **Шапки нет.** Всё, что в ней
стояло, было второй копией того, что и так на экране: бренд и текущий раздел —
в меню, три точки — в строках служб, «всё в порядке» — в чеклисте. Копия
факта — это место, где можно ошибиться, и платит за ошибку тот, кто читает,
то есть человек. **Добавляя страницу, не добавляй в неё копию статуса** и не
заводи второе место для одного и того же числа: если факт некуда положить, его
некуда и рисовать.

### Три экрана, и ни один не повторяет другой

| Экран | Работа |
|---|---|
| `Server` | одна строка «можно ли играть», блок «Что нужно сделать» (только при проблеме), три плитки, всегда раскрытые строки служб с чеклистом и разбивкой по базам |
| `Backups` | **создаёт** копию (прогресс, отмена, итог), **откатывает** по полной копии и **удаляет** любую; напоминание; список копий из `backups\`; свободное место на диске |
| `More` | четыре свёрнутых раздела: персонажи с поиском, аккаунты с поиском, шесть проверок с подсказками, папки сервера |

**Строки служб раскрыты всегда и без заголовка.** Свёрнутый блок был компромиссом,
который купил две вещи и стоил одной: кнопки служб прятались до запроса, а
чеклист не занимал место — но чеклист это единственное, что отвечает на
«что панель вообще делает», а заголовок, который надо кликнуть, чтобы понять, что
внутри, это заголовок, который не кликают. Наверху остаётся вопрос, на который
есть один ответ, и одна кнопка. Кнопка «Создать копию» на главном экране
тоже убрана: у копий есть раздел, а у ярлыка, чей прогресс живёт в другом
месте, люди жмут его дважды.

**Ниже hero живёт по одному условию: `hub.dataReadable`.** Пока MySQL поднят
(или кто-то упал) — показываются плитки «из чего состоит реалм» и ошибки чтения;
пока база лежит — блока нет вообще. Причина не в удобстве: лестница остановки
гасит MySQL **после** мира, поэтому недоступная база — это следствие нажатой
кнопки, а не поломка. Экран, который на это ругается, жалуется на собственное
действие, и «База отвечает — dial tcp 127.0.0.1:3306» на выключенном мире было
именно этим.

**Блок «Что нужно сделать» показывает только то, чего человек не сделал сам.**
Из чеклиста бэкенда выпадают две позиции:

* `server` («Сервер запущен») — кнопка выше уже предлагает запустить;
* `database` («База отвечает») — пока MySQL лежит.

Остальные (`repack`, `rollback`, `space`) читаются из папок, а не из базы, так
что остаются верными при выключенном мире и остаются достойными сообщения:
устаревшая
копия — единственное, что тут можно сделать, не запуская ничего.

**Плитка «Копий на диске» удалена намеренно.** Она читалась из `backups\`, а не
из базы, поэтому была единственной, что выживала при выключенном мире — то есть
единственным источником шума на пустом экране. Плюс у неё есть свой раздел.
Плитка аккаунтов поставлена третьей, чтобы строка не разъезжалась на две.

Чеклист «Настройка реалма» — не раздел «Проверки». Тот диагностирует шесть
технических фактов о трёх процессах, этот отвечает на один вопрос в терминах
пользователя («реалм сейчас играбелен?») и называет, что починить. Считается он
на бэкенде из того, что у приложения уже есть (layout, снимок данных,
supervisor), поэтому разойтись с экранами, которые он обобщает, не может.

Правило «ни одно число не рисуется в два места, которые могут разойтись» после
переезда на Svelte держится само: значение живёт в `hub` один раз, а экраны
читают производные от него. Агрегат на «Сервере» и разбивка в «Технических
деталях» — пара «сводка/детали» из одного `$derived`, а не две ветки
отрисовки.

| Файл | Ответственность |
|---|---|
| `frontend/src/App.svelte` | оболочка: сайдбар, нижняя полоса (последнее действие + обновление), оба диалога. Шапки нет |
| `frontend/src/routes/*.svelte` | три экрана; в `More` — переключатель языка |
| `frontend/src/lib/state.svelte.ts` | `hub` — единственный источник состояния и единственная подписка на события Wails |
| `frontend/src/lib/i18n.svelte.ts` | реактивный язык, `t()`/`P()`/`form()` и хелперы над ключевыми семействами (`stateLabel`, `svcPlain`, …) |
| `frontend/src/lib/i18n/*.ts` | словари семи языков; `en.ts` — эталон ключей, остальные сверяются с ним через `satisfies` |
| `frontend/src/lib/words.ts` | нетекстовые таблицы: `SERVICE_NAME`, `SETTLED`, `CHECK_OWNER`, `HAS_ADVICE`, `CAN`, `RESTORABLE`, `RENDER_MAX` |
| `frontend/src/lib/format.ts` | числа, байты и даты по правилам текущего языка (`Intl`, таблицы единиц) |
| `frontend/src/lib/api.ts` | единственное место, где импортируются `wailsjs`-биндинги |
| `frontend/src/lib/components/ui/*` | компоненты shadcn-svelte, их не правим |
| `frontend/src/app.css` | тема: тёмная, золото как акцент, поверх `@import "tailwindcss"` |

**Второго места для импорта биндингов нет.** Новый компонент берёт
`hub`, а не `wailsjs` напрямую: два места импорта — это два места, которые надо
поменять при добавлении метода на `App`.

**`hub` — единственный, а не «один из».** Его состояние `$state`, поэтому
изменение поля перерисовывает всех, кто его читает. Второй экземпляр означал бы
две подписки на события и два набора кнопок, которые решают разное.

### Языки (i18n)

Панель говорит на семи языках: en, ru, zh, es, pt, fr, de. Правила:

- **Русский — источник.** Словарь `internal/i18n/ru.go` переносит строки,
  которые были в коде, байт в байт; `frontend/src/lib/i18n/ru.ts` — строки,
  которые были в разметке. Тесты пинят русский (`i18n.Set(i18n.Ru)` в
  `TestMain`), поэтому перевод не должен переформулировать русские фразы.
- **en — эталон ключей.** `internal/i18n/en.go` и `frontend/src/lib/i18n/en.ts`
  определяют полный набор; тест паритета (Go) и `satisfies Record<keyof
  typeof en, string>` (фронт) не дают языку разойтись с эталоном. Формы
  множественного числа живут под `key.one/.few/.many/.other`; en несёт только
  `one`/`other`, остальные — сколько нужно (правило категорий — `cat()` в Go,
  `Intl.PluralRules` на фронте).
- **Кто что переводит.** Бэкенд строит свои предложения сам (чеклист,
  проверки, ошибки) и переводит их до отправки — фронт рендерит его текст
  как есть. Строки разметки и `state.svelte.ts` идут через `t()`. Строки
  файлового лога (`logf`, `logger.Info/Error`) не переводятся сознательно —
  у них другой читатель.
- **Переключение живое.** `AppService.SetLanguage` валидирует код, сохраняет
  его в `wow-hub.settings.json` (`Settings.Language`, пусто = определить по ОС
  при первом старте) и переэмитит расписание; фронт после ответа дёргает
  `loadSetup()` и `refreshData()`. Трей обновляет свой язык только после
  перезапуска — он собирается один раз до окна.
- **Добавить язык** = файл словаря в `internal/i18n` + запись в
  `i18n.Languages`/`i18n.Names`, файл в `frontend/src/lib/i18n` + запись в
  `LANGS`, запись в таблицах единиц `format.ts` — и ничего больше.
- **Харнесс** (`tools/ui-e2e.mjs`) стабом отдаёт `Language: 'en'` и пинит
  английские литералы: локаль машины, на которой он гоняется, не должна
  решать, какой текст ждут проверки.

### Данные только для чтения

Три экрана питаются **одним** снимком `main.DataSnapshot`, который бэкенд
толкает событием `data`. Ни один из них ничего не пишет — ни в базу, ни в
файлы; `internal/realmdb` и `internal/backups` состоят из одних `SELECT` и
`ReadDir`.

* **Почему снимок, а не запрос.** Запрос размеров — 0.68 с на прогретом
  InnoDB и ~10 с на холодном (`information_schema_stats_expiry = 86400`).
  Привязка, которая столько блокируется, читается как зависшее окно. Поэтому
  `RefreshData()` возвращает управление сразу, а ответ приходит событием.
* **`Loaded` существует не для красоты.** Страница читает кэш снимка при
  загрузке, чтобы нарисовать сразу. Пока ни одного чтения не завершилось, она
  обязана отличать «здесь пусто» от «я ещё не смотрела» — это ровно та же
  причина, по которой у `Inventory` есть `Err`, а не пустой список.
* **Одно чтение за раз.** Триггеров три: медленный таймер (раз в 60 тиков),
  смена состояния MySQL и кнопка. Триггер, пришедший во время чтения, не
  запускает второе — он запоминается в `dataAgain` и отрабатывает после, чтобы
  последний запрос не потерялся, а база не получила два параллельных агрегата.
* **Смена состояния MySQL — отдельный триггер.** Именно она делает числа
  неверными: пока MySQL лежит, читать нечего, а как только поднялся — снимок
  на экране устарел. Ждать таймера значило бы держать «нет подключения к базе»
  на экране до минуты после того, как база вернулась.
* **Не прочитанное число не показывается как ноль.** `val: null` в плитке
  рисуется приглушённым тире, а не нулём; ошибки чтения — отдельной строкой
  под плитками, «папку не прочитали» и «в папке пусто» — разными элементами.
* **`wails build` печатает `Not found: time.Time`** — это генератор
  TypeScript-деклараций, а не компилятор. `time.Time` попадает в
  `frontend/wailsjs/go/models.ts` как `any`, и по сети всё равно едет строка
  RFC 3339, которую разбирает `stamp()` в `format.ts`. Предупреждение
  косметическое; заменять поля на строки в Go ради тишины не нужно.

### Создание копии и откат

Форматы — **форматы, которые уже были в репаке**, и это не лень. Копия без
остановки — это четыре файла `mysqldump`, снятые теми же флагами, что
`backups\backup-table.cmd`, и разложенные так, как ждёт
`backups\restore-all-db.cmd`. Полная копия — zip с записями, укорененными в
`mysql/data/`, как делал старый скрипт `snapshot-mysql-data.cmd`, но пишет её
теперь встроенный архиватор `internal/archive`: ни скрипт, ни установленный
7-Zip панели больше не нужны, а ручная распаковка любым unzip-инструментом в
корень репака по-прежнему возвращает базу на место. Второй формат, придуманный
здесь, дал бы два набора похожих файлов, которые не заменяют друг друга, — и
выяснилось бы это в худший возможный день.

* **`restore-all-db.cmd` берёт самую свежую папку с `acore_world.sql` и
  МОЛЧА пропускает базу, файла которой нет.** Неполная папка даёт реалм, где
  world и characters из разных дней, и скрипт при этом сообщает об успехе.
  Поэтому `backups.Point.Note` существует и показывается на экране — и
  поэтому кнопки «Восстановить» у таких копий нет вовсе.
* **Прогресс идёт шагами, а не байтами.** Четыре базы различаются по размеру
  на порядок, и размер схемы неизвестен, пока она не вылита.
* **Полная копия требует остановленного MySQL**, копия без остановки — наоборот,
  работающего. Это первое, что нужно знать про кнопку, поэтому `kind-meta`
  под каждой кнопкой говорит текущее состояние, а не только описание.
* **Создание не идёт через `run()`.** Тот на две минуты гасит всю страницу и
  пишет «готово» в строку службы, которая к дампу отношения не имеет. У копии
  своя полоса прогресса, своя отмена и свой итог.
* **Экран написан словами человека, а не предметной областью.** «Дампы баз»
  и «слепок mysql\data» были оба точны и оба непонятны: кто не знает, что
  такое дамп, не выберет из двух кнопок, а разница между ними решает, надо ли
  останавливать сервер. Отсюда «Копия без остановки сервера» и «Полная копия».
  Форматы не менялись — они описаны в комментариях `internal/dumps` и
  `internal/restore` и в `backups/README.md`.
* **Откат — отдельное окно подтверждения, а не тот же диалог, что и «убить
  процесс».** Тот спрашивает «процесс не умер, убить?», этот — «выбросить
  базу?». Под одной шапкой формулировки пришлось бы сгладить так, что не
  значили бы оба.
* **Откат оставляет сервер выключенным** (`Screen = left stopped`, решение
  пользователя): старт автоматически означал бы ещё и старт с теми учётками,
  что оказались в восстановленной базе.
* **Откат пишет в тот же `BackupStatus` и в ту же полосу прогресса**, что и
  создание. Второй тип был бы вторым путём отрисовки одного состояния — тем
  самым, из-за которых расходятся экраны. Различает их `Kind == "restore"`.
* **Страховка делается отдельным `dumps.Runner` без прогресс-стока.**
  Снимок сам себя объявляет `physical`-бэкапом, и его отчёты переписали бы
  шаг отката на «acore_world» посреди распаковки.

### Напоминание

`wow-hub.settings.json` рядом с exe (в git не попадает — состояние конкретной
машины, см. корневой `.gitignore`). Не в `%APPDATA%`: репак — папку переносят,
а настройки, оставшиеся на старом месте, описывали бы не тот реалм.

* **На экране одна галочка и одно поле.** «Создавать самой» и «Отложить на
  день» убраны из UI, а `AutoRun`/`SnoozedUntil` остались в настройках:
  значение `AutoRun` при сохранении отправляется **из последнего снимка**,
  а не как `false`. Иначе настройка, включённая старой сборкой или рукой в
  json, молча выключалась бы тем, что её галочки больше нет.
* **По умолчанию напоминание выключено, автосоздание — тоже.** Копия без
  остановки — это 385 МБ и около двух минут записи на диск; запускать такое
  без спроса, пока человек играет, — не услуга. Включить напоминание —
  решение пользователя, и только такое решение переживает свою ошибку.
* **Интервал из расписания — тот же порог, по которому чеклист считает точку
  свежей** (`App.rollbackStaleAfter`). Иначе панель говорила бы «три дня
  нормально» и «пора» про одну и ту же папку.
* **`LastRun` двигается только при успехе, `LastAttempt` — при любой попытке.**
  Если бы неудача двигала `LastRun`, дамп, которого не было, заглушал бы
  напоминание на неделю. `LastAttempt` нужен потому, что планировщик живёт на
  секундном цикле: без него одна неудача превратилась бы в тысячу попыток,
  каждая из которых сначала пишет частичный файл.
* **Ошибка чтения файла настроек не глотается.** Расписание, которое молча
  вернулось к значениям по умолчанию, человек обнаружит только по пропущенной
  неделе напоминаний.

### Правила, которые уже стоили времени

* **Один проход отрисовки на обновление.** `renderStatus()` рисует индикаторы,
  hero, строки, проверки и баннер; `renderHealth()` — проверки и баннер;
  `renderData()` — плитки, замечания, диск, точки, таблицу баз и возраст
  данных. Второй путь отрисовки того же состояния — это и есть то, как экраны
  разъезжаются между собой.
* **`CAN` — единственное место, решающее доступность кнопок.** Строки берут
  из него по `data-act` и состоянию службы; общие «Запустить всё» /
  «Остановить всё» — производные от него же (`some(s => CAN.start[s.State])`),
  а не собственное правило. Пустой снимок (первый `Status()` ещё не пришёл
  или упал) оставляет **всё** включённым: отказ действовать из-за того, что
  панель не может прочитать своё состояние, — худший из возможных режимов.
* **Недоступная проверка — не всегда проблема.** Порт намеренно
  остановленного мира обязан быть закрыт. Сбой проверки считается настоящим
  только когда её служба в «устоявшемся» состоянии (`running`, `external`,
  `failed`); иначе строка помечается нейтрально. Без этого значок «внимание»
  горит всегда, и его перестают читать. Правило — `SETTLED` в `words.ts`.
* **«Запущен ли сервер» считается в двух местах, и это уже разошлось однажды.**
  `setupServer` в `app.go` считает на бэкенде, `upCount` во фронтенде — и бэкенд
  принимал только `StateRunning`, а фронтенд ещё и `StateExternal`. Итог: чеклист
  показывал «запущено 1 из 3» под работающим миром, пережившим панель, и советовал
  нажать «Запустить сервер» — а тот запустил бы второй мир. Теперь оба считают
  одинаково, на правило есть тест, и правило чеклиста: **процесс, который панель не
  запускала, всё равно запущен** — различается `Owned`, а не живость.
* **Красный восклицательный знак должен всегда означать «нужно действие».**
  Отсюда три значка, а не два: `✓` — прошло, `!` — настоящий сбой с
  подсказкой «что делать», `·` — нейтрально.
* **Русские числительные — через `plural()`.** «1 проверок» читается как
  баг; 11 и 12 требуют формы «проверок», хотя оканчиваются на 1 и 2.
* **Никакого `{@html}`.** Имена персонажей и имена папок в `backups\` — это то,
  что ввели их владельцы. Svelte экранирует `{текст}` по умолчанию, и это
  единственная причина, по которой безопасность здесь не отдельная работа.
* **Список персонажей грузится при первом открытии раздела**, а не при
  запуске: это на порядок больше данных, чем всё остальное, и в большинстве
  сессий в него не заходят. Отрисовка ограничена `RENDER_MAX` строками, а
  поиск при этом идёт по всем — счётчик над списком говорит, сколько нашлось.
* **Окно без системной рамки (`Frameless: true`), полосу рисует страница.**
  Три кнопки в `App.svelte` вызывают `WindowMinimise`,
  `WindowToggleMaximise` и `Quit` из рантайма Wails. Крестик зовёт именно
  `Quit`, а не `window.close()`: `OnShutdown` намеренно **не** гасит сервер, и
  это поведение обязано пережить смену рамки.

  Полоса пустая намеренно: заголовок в ней повторил бы бренд из меню, а это
  ровно та ошибка, которую три последние правки вычищали. Её работа — быть
  зоной, за которую окно таскают.

* **`--wails-draggable: drag` — не наш CSS.** Это custom property, которую
  читает рантайм Wails: на нажатии, начавшемся внутри элемента с ней, вызывается
  Win32-перетаскивание окна вместо выделения текста. Поэтому в `app.css` это
  литерал в `@layer components`, а не утилита Tailwind и не `@apply`. Кнопки
  внутри зоны перетаскивания остаются кнопками — рантайм таскает только если
  нажатие началось на самой зоне, — поэтому у них `cursor: default`.

* **`BackgroundColour` задан по той же причине, что и `Frameless`.** Без
  системной рамки нечего спрятать первую отрисовку, и белый дефолт мигнул бы
  перед тёмным фоном страницы. Значение совпадает с `--background` в `app.css`;
  при смене темы менять оба.

* **Чего frameless не умеет и мы не чинили.** Системного меню окна (правый
  клик по заголовке) нет. Превью окна в панели задач Windows 11 нет — для него
  нужен `WS_EX_COMPOUND` из сырого Win32, а это вторая обёртка ради косметики.
  Всё это проверено **только вручную**: окно из агентской песочницы не
  поднимается, e2e крутит только страницу и умеет проверить лишь то, что
  кнопки доходят до рантайма.

* **Откат:** тег `before-frameless`. Возврат — `git revert` коммита с рамкой
  плюс пересборка, либо `git checkout before-frameless -- wow-hub/` если нужно
  вернуться не откатывая, а просто посмотреть.

* **Hero на «Сервере» упразднён — он был третьим дублем подряд.** Заголовок
  «AzerothCore» повторял бренд из меню, абзац «локальный мир…» ничего не
  сообщал, а большая кнопка «Запустить мир» вызывала ровно тот же `StartAll`,
  что и «Запустить всё» двумя сотнями пикселей ниже. Осталась одна строка —
  «можно ли в игру» — потому что такой фразы больше нигде нет: точки в строках
  служб говорят, **какая** служба лежит, а нельзя ли играть. Кнопки запуска и
  остановки теперь живут в блоке служб, стали главным действием экрана и
  переименованы в «Запустить мир» / «Остановить мир».

* **Заголовок над пустым списком — обещание, которое страница не держит.**
  Чеклист приходит отдельным чтением позже служб, и под заголовком
  «НАСТРОЙКА РЕАЛМА» секунду висело ничего. Блок ждёт `hub.setup.length`.
  Проверка на мелькание это не ловит: там исчезающие строки, а не
  отсутствующие.

* **Две кнопки с одним `data-role` — строгий режим Playwright.** У переключателя
  мира их две, «Запустить мир» и «Остановить мир», и видна ровно одна, поэтому
  локатор в e2e `[data-role="world-toggle"]:visible`. Без `:visible` он
  резолвится в обе, и каждый клик падает как нарушение строгого режима.

* **Крестик спрашивает, когда работает хоть одна служба, и отказ отменяет
  закрытие.**
  Мир переживает панель (`WinOps.Start`), поэтому «закрыть панель» и «оставить
  мир работать» больше не одно и то же. Крестик зовёт `hub.closeWindow()`:
  **поднята хоть одна из трёх** — диалог (`components/QuitAsk.svelte`), все
  выключены — выход сразу. Одной из трёх достаточно: база и вход подняты почти
  всегда вместе с миром, и панель, закрытая над ними, оставляет базу писать в
  пустоту. Что именно работает — диалог называет списком.
  «Остановить и выйти» идёт **первым**, потому что труба, которой пишется
  `server shutdown 1`, живёт только пока жива панель: это единственный момент,
  когда остановка измеренная, с отсчётом и сохранением. Отказ отменяет
  закрытие, а не «закрывает вопреки»; оставить серверы работать можно из трея
  («Выход»).
  **Провалившаяся остановка не закрывает панель.** Значит мир жив, и тот, кто
  может это видеть, — панель.
  `StopAll` и `Quit` уже были биндингами — новых не появилось, генерировать
  bindings не пришлось.
  **Перехватить Alt+F4 или «Выход» в трее нельзя:** в Wails v3 beta.27 нет
  `OnBeforeClose`, есть только `OnShutdown`, а он запускается уже после
  решения и отменить его не может. Если в beta появится перехват — вопрос
  возвращается.
  **Раздел 3 e2e держит состояниеStack-а:** он кладёт все службы и поднимает
  обратно, потому что дальше проверяется приход мира рядом с ними. Плюс
  крестик в нём теперь открывает окно вопроса — это проверяется там же.
* **Сворачивание закрывает окно, а не прячет его.**
  Спрятанное окно держит WebView2, а это **~285 МБ в шести процессах**. Кнопка
  «Свернуть» зовёт `Window.Close()`, панель возвращается из трея новым окном.

  Замерено на живой сборке: с окном 18 процессов `msedgewebview2`, после
  закрытия окна — 12, и `wow-hub.exe` остаётся жив. Оставшиеся 12 не наши:
  их родители — `SearchHost` и `Widgets`.

  Почему так, а не «прятать»: в Wails v2 скрытие окна не убивает webview, и
  освободить память было нечем — v2 не умеет ни уничтожать окно, ни гасить
  webview, не дав ему умереть вместе с процессом. В v3 `window.Close()`
  уничтожает окно вместе с webview, а `DisableQuitOnLastWindowClosed` оставляет
  приложение жить, и трей его возвращает.

  Почему не выход по сворачиванию, как пробовали: Windows сворачивает окно и
  при Alt+Tab, и при Win+D, и кликом по панели задач — панель исчезала сама, без
  воли человека. Теперь сворачивание только по кнопке.

  Возврат — `app.Window.NewWithOptions`, а не `Show()`: закрытое окно не
  воскресить (`Run()` выходит по непустому `impl`). Новое окно открывается на
  экране «Сервер» и с пустым кэшем данных — это штатно, `DataSnapshot.Loaded`
  отличает «читаем» от «пусто».

* **Левый клик по иконке в трее открывает панель, правый — меню.**
  Своего `OnClick` у трея не будет дефолтом: Wails назначает обработчик
  левого клика только когда трей привязан к окну через `AttachWindow`, а у нас
  окно пересоздаётся и привязывать нечего. Без `tray.OnClick` иконка
  декоративная — панель возвращается из меню и больше ниоткуда.

  `showPanel` (метод `eventSink`) общий для клика по иконке и пункта меню:
  показать текущее окно, а если его нет — построить новое.

* **Внутри создания окна колбэк трея входит повторно — блокировка там вешает
  панель.** Wails поднимает webview, прокачивая очередь сообщений
  (`pumpUntilInited`), поэтому второй клик по иконке приходит в `showPanel` изнутри
  первого, на том же потоке. Мьютекс, взятый на время создания окна, даёт
  взаимную блокировку: второй ждёт лок первого, первый ждёт насос, в котором
  сидит второй. Панель замирает навсегда — окно создано, но не показано.

  Проверено: сначала это выглядело как «два окна», и мьютекс на время сборки
  превратил дубликат в зависание. Правильное решение — **не держать блокировку
  через создание окна**: решение «строить или показывать» принимается под коротким
  локом, флаг `building` не даёт второму клику начать вторую сборку, а пришедший
  во время сборки просто выходит и не показывает ничего — панель покажет та
  сборка, что уже идёт.

  `build` и `present` внедряются параметрами не для красоты: `Show()` в v3 читает
  пакетный глобал, который есть только внутри запущенного приложения, и sink,
  который проверяется лишь в живой GUI, — это sink с непроверяемым поведением.
  Именно так и появились два окна.

  Проверено вживую десятью кликами подряд по трею: окно одно и то же
  (`hwnd` не меняется, 18 процессов WebView2).

* **Выход — только из трея, крестик тоже.** `Quit` завершает приложение, и
  `OnShutdown` намеренно **не** гасит сервер. Сервер остаётся жить в обоих
  случаях; разница только в том, остаётся ли панель в трее.

* **Провал в чеклисте не дублируется ниже.** Блок «Проверено, всё в порядке»
  показывает **только прошедшие** строки. Провалившиеся уже сказаны словами в
  «Что нужно сделать» наверху; повторять их с сырой ошибкой Go было третьим
  упоминанием одного факта на одном экране (первое — в блоке проблем, второе
  и третье — здесь и в строке ошибки под таблицей). Строка ошибки под таблицей
  баз убрана по той же причине.

  Строка `database` исключена дополнительно: её подробность — «4 баз, 1,2 ГБ,
  380 аккаунтов», и все три числа уже на экране (размер и аккаунты — в
  плитках, таблицы — в разбивке ниже).

* **`humanBytes` обязан совпадать с `bytes()` во фронтенде.** Go печатает `%f`
  точкой в любой локали, поэтому размер баз выходил на экране двумя
  способами: «1.2 ГБ» из чеклиста и «1,2 ГБ» из плитки — одна величина, два
  числа, и глаз видит разницу. Запятая ставится руками через `strings.Replace`,
  и десятичный знак ставится только ниже десяти, как в `bytes()`. Тест
  `TestHumanBytesUsesTheLargestUnitThatFits` закрепляет запятую.

* **Чеклист и таблица баз разведены по панелям.** Это разные предметы, а одна
  строчка мелких заглавных букв между ними не разделяла ничего: глаз искал,
  где кончилось одно и началось другое. Таблица получила свою рамку, шапку
  колонок и выравнивание чисел вправо.

* **Ничего не мелькает при открытии окна, и это проверяется.** Плашка «проверки…»
  в значке сменялась «всё в порядке» — два слова-вердикта подряд в одном углу,
  причём пауза между ними равна времени `Health()`, то есть на тёплой машине
  несколько миллисекунд: глаз успевает дойти, прочитать нечего. То же с
  «нет данных» в разбивке по базам, где ничего не смотрели, и с «Данные
  читаются…», которую `start()` вообще ставил последним чтением, после
  `Health()`.

  Правило одно на все три: **надпись не появляется раньше, чем её успевают
  прочитать.** Пустой слот не меняется; надпись, которой нужны 700 мс,
  появляется после 700 мс (`PENDING_NOTICE_MS`) и только если чтение ещё идёт.
  На тёплом кэше она не появляется вообще. Снимок читается параллельно со
  всем остальным, а не в конец очереди — иначе надпись висит столько, сколько
  шли проверки, причём проверки к числам отношения не имеют.

* **Проверка мелькания — в e2e, а не «посмотрел глазами».** `window.__flash`
  пишет все текстовые узлы на каждом кадре, окно замораживается на экране
  «Сервер» (на последнем экране прогона сравнивалось бы начало с чужим
  экраном, и мелькнувшим сочлось бы всё подряд). Любая строка, которая была
  видна и пропала, — это мельканье по определению.

  Тут же ловушка, из-за которой проверка сначала была зелёной на сломанном
  коде: заглушка отвечала мгновенно, и все надписи появлялись и исчезали внутри
  одного кадра — то есть мигания не было физически. `Health()` в заглушке
  ждёт 700 мс намеренно, и по той же причине готовность страницы ждёт не
  первую отрисовку, а вызовы `Data()` **и** `Health()`: `start()` ждёт их
  по очереди, и экран может выглядеть готовым, не получив снимка.
* **Проверки условий, а не «блок существует».** Раздел 5 e2e ставит сервисы
  выключенными **все три**, а не только мир: с поднятой MySQL база читается и
  числа по делу, проверять было бы нечего. Затем поднимает обратно и ждёт, что
  плитки вернулись. Обе половины условия обязаны быть в тесте — иначе он
  проходит и на удалённом блоке, и на блоке, который ничего не скрывает.
* **Проверка не должна искать текст по всей странице.** Свёрнутые «Технические
  детали» держат в DOM полный чеклист с подписями, и `body.includes('Сервер
  запущен')` находит надпись в секции, которую никто не открывал и читать не
  должен. Проверять надо сам блок `[data-role="problems"]`.
* **`toLocaleString('ru-RU')` ставит узкий неразрывный пробел.** «1 420» в
  проверке сравнивается с символом, который страница вывела; пробелы
  нормализуются в обёртке `text()`.
* **`hub.busy` — это про блокировку на время операции, и ничего больше.**
  Второй счётчик означал бы две подписки на события и два набора кнопок.
  «Отменить» обязана быть живой ровно тогда, когда остальные мертвы —
  и невидимой во время отката, который отменить нельзя (см. пункт выше
  про `internal/restore`).
* **Кнопка «Откатить базу к этой копии» есть только у полных копий.** У остальных
  строка говорит, чем их возвращать, потому что `restore-all-db.cmd` берёт самую
  свежую папку, а не запрошенную, — кнопка сделала бы не то, что написано.

  **Почему не «Вернуть»** (было до 2026-10-03, человек указал): глагол без
  объекта, и по соседству с «Удалить» читался как обратное к ней действие —
  «вернуть на место». Обещает он ровно противоположное тому, что происходит:
  данные не возвращаются, а пропадают. «Откатить базу к этой копии» называет и
  действие, и его предмет. Слово «откатить» тут и оставили: панель уже говорит
  о точках отката в чеклисте, то есть термин на экране уже есть.

  **Строка под копией — только там, где кнопки нет.** Раньше она была
  припиской к кнопке («кнопкой «Вернуть»»), то есть вторым местом одного и
  того же факта — правило «ни один факт не рисуется в два места». У копии без
  кнопки строка остаётся: это единственное место, где сказано, что откат есть
  и куда идти.

* **Стража на имя папки одна, и лежит в `backups.Resolve`.** Имя приходит со
  страницы, а путь строится из него — значит риск один на всех, кому это имя
  нужно превращать в путь: распаковке и удалению. Раньше проверка жила в
  `restore.archiveOf`; когда появилось удаление, копия была бы второй, и рано
  или поздно они разошлись бы. `Resolve` требует, чтобы папка существовала и
  была папкой: `os.RemoveAll` считает отсутствующий путь успехом, и удаление
  без этой проверки отвечало бы «удалено» про копию, которой не было.

* **«Удалить» тише, чем «Откатить», и это не украшение.** Красный в строке
  значит «это заменит базу»; два красных рядом не сказали бы ни того, ни
  другого. Вес удаления стоит в диалоге `DeleteAsk`, где папка названа словами
  вместе с датой и размером, и сказано прямо, что вернуть будет нечем.
* **Снимок засевает элементы управления, но не переписывает их.**
  `$effect` в `Backups.svelte` пересчитывается на любое изменение, а снимок на
  бэкенде в этот момент ещё старый — потому что сохранить никто не успел.
  Первая версия писала значения в поля на каждой отрисовке, и установка второй
  галочки снимала первую. Помогает не «пропустить элемент в фокусе» (снимается
  как раз НЕ тот, что в фокусе), а засевать поля только когда пришёл
  действительно новый снимок — по подписи `seeded` в `Backups.svelte`.
* **`AutoRun` возвращается из последнего снимка, а не как `false`.** Галочки
  «создавать самой» на экране нет; настройка, включённая старой сборкой, иначе
  молча выключалась бы тем, что её галочки больше нет.

### Как это проверять

Окно приложения из агентской песочницы не поднимается (см. заметки в
`../.workbuddy-ai/memory/`), поэтому внешний вид проверяется **в настоящем
браузере**: **`tools/ui-e2e.mjs`** гоняет `frontend/dist` в Chromium через
Playwright, с подставленным бэкендом.

```bash
npm --prefix frontend run build     # сначала собрать dist - харнесс берёт его
cd "C:/Users/False/.workbuddy-ai/binaries/node/workspace"
node "<abs>/wow-hub/tools/ui-e2e.mjs" "<abs>/wow-hub/frontend/dist" "<abs>/shots"
```

Скрипт копируется в рабочий каталог node: `playwright` там, а не в репаке, и
ES-импорт резолвится от расположения файла, а не от `cwd`.

**`tools/check-frontend.mjs` удалён, и это не потеря.** Он сверял id в разметке с
`$('id')` в скрипте — сверку, которой в Svelte занимается компилятор: опечатка в
импорте компонента падает на `npm run build`. Оставаться должна одна проверка,
которая ловит то, что компилятор не видит: **работает ли собранная страница**.

Что харнесс проверяет и почему именно это:

* сборка загрузилась и первый ответ `Status()` отрисован (`[data-role=headline]`),
  а не «страница открылась»;
* мир выключен, а подняты две службы из трёх → заголовок говорит, что мира нет,
  и **не** обещает игру;
* мир выключен **и MySQL погашен вместе с ним** → ни блока проблем, ни плиток,
  ни строки ошибки чтения, а устаревшая копия остаётся названа;
* мир и база снова подняты → плитки вернулись с числами, счётчика копий среди
  них нет;
* кнопка мира вызывает `StartAll`, и после подъёма мира сама становится
  «Остановить мир» и вызывает `StopAll`;
* «Что нужно сделать» показывает устаревшую копию и **не** показывает
  остановленный мир;
* кнопки служб видны без клика и следуют `CAN`: «Запустить» у работающего
  сервиса серая; на главном экране нет ни кнопки раскрытия, ни «Создать
  копию»;
* полная копия сера при работающем мире, и подпись говорит «сначала остановите»;
* «Откатить базу к этой копии» есть только у полной копии, диалог открывается,
  ответ уходит в `RestoreSnapshot`;
* под полной копией нет строки, повторяющей кнопку, а под копией без кнопки —
  есть `restore-all-db.cmd`;
* «Удалить» есть у каждой копии, диалог говорит, что вернуть нечем, «Оставить»
  не вызывает `DeleteBackup`, «Удалить» вызывает его с именем папки;
* прогресс копии показывает шаг, «Отменить» живая, а во время отката её **нет**;
* списки грузятся при открытии раздела, поиск фильтрует;
* упавшая проверка у работающей службы называет действие, у остановленной — нет;
* диалог подтверждения приходит событием и уходит по ответу, `confirm-cancel`
  его закрывает;
* страница не бросила ни одной ошибки и в консоль не писала.

Ловушки, все уже стоили прогона:

* **Без `await` харнесс врёт.** Каждая проверка — промис.
* **`file://` не годится** — браузер блокирует ES-модули, страница загрузится с
  мёртвыми кнопками, а проверки на статическом документе всё равно пройдут.
* **`EventsOn` в сгенерированном биндинге — это `EventsOnMultiple`, а та
  принимает список имён.** Заглушка обязана оборачивать строку в массив, иначе
  `"status"` распадается на шесть однобуквенных каналов, события не приходят, и
  все ассерты падают на пустом месте.
* **Доступное имя кнопки не уникально.** Кнопка «Ещё» в меню упоминает
  «Персонажи» в подписи, поэтому `getByRole('button', {name: /Персонажи/})`
  находит две. Разделы ищутся по `[data-accordion-trigger]`.
* **Готовность — не `load`.** Первая отрисовка ждёт ответа `Status()`, поэтому
  ждём `[data-role=headline]`.
* **Триггер проверки может быть неготов.** Например, «остановленный мир не назван
  поломкой» имеет смысл только когда мир действительно остановлен, а после
  предыдущего раздела он поднят. Условие проверки обязано ставить состояние
  само, иначе она проверяет не то, что написано в сообщении.
* **Падение в середине не должно съедать результаты** — `process.on('exit')`
  печатает уже собранные ошибки.
